# Vision

## The problem this repository answers

Spec Kitty ships a large, multi-domain set of **built-in doctrine** as a single monolithic bundle,
and its default behaviour is "activate everything when not explicitly constrained." A consumer
project that skips the (unenforced) charter step inherits the whole corpus and **floods every LLM
session's context** with doctrine it does not need.

`spec-kitty-open-packs` replaces the monolith with **coherent, composable, opt-in packs** — domain
and purpose slices a team adopts deliberately, composed both **vertically** (built-in → org →
project) and **horizontally** (independent packs, and compound packs via `depends_on`).

## The vision statement

> **`spec-kitty-open-packs` is the canonical, curated, community-friendly publishing home for Spec
> Kitty doctrine packs — where every pack is discoverable, documented straight from its source, and
> verifiable by checksum before it is trusted.**

Three commitments follow from that sentence:

1. **Canonical & curated.** SK Inc. maintains and curates the catalog; community contributions are
   highly welcomed through a low-friction path. This is the single place to find, compare, and pull
   a pack — and the single place to validate one.
2. **Documented from source, not by hand.** The docsite's reference content is **generated from the
   actual code structure** (the pack directories and the validator), so documentation cannot drift
   from reality and adding a pack requires (ideally) **no documentation authoring at all**.
3. **Verifiable by checksum.** Every pack is **checksum-tagged** so a downloaded copy can be
   compared against the published hash — the foundation of a graduated trust story for a repository
   that may eventually ship executable gate assets.

## Where the docsite fits

The docsite is the **public face** of these commitments. It must be:

- **Simple to create and maintain** — a small OSS team should not hand-maintain per-pack pages.
- **Content-from-code** — pack reference pages and the catalog table are generated by walking
  `packs/*/` and running the validator; guides, vision, and decisions are hand-authored and stable.
- **Simple, single-language toolchain** — same Common Docs conventions and the same generate → build →
  GitHub Pages *pattern* core already operates, realized on MkDocs Material so the validator, generator,
  and site all live in Python ([ADR-1](adr/2026-07-18-1-mkdocs-material-as-docsite-generator.md)). The
  long-term aim is one look and one maintenance model across both repos by standardizing on MkDocs.
- **Trust-surfacing** — each generated pack page shows its integrity block (version, checksum, trust
  tier) so evaluators can judge a pack before adopting it.

## Division of responsibility (unchanged)

| Concern | Lives in |
| --- | --- |
| Doctrine artifacts, packs, compound packs, **the docsite** | **this repo** (`spec-kitty-open-packs`) |
| Pack authoring & usage guides | **this repo** (`docs/guides/`) |
| Doctrine mechanics, resolution, DRG, activation | core (`Priivacy-ai/spec-kitty`) |
| Pack **manifest schema, validator, checksum/verified distribution** | core (consumed here) |

The docsite direction leans on core work that is **planned but not fully landed** — the pack
manifest schema (core #2467), the reusable validator surface (#2471), and checksum/verified
distribution (#2539/#2543). The [docsite design](docsite-design.md) is explicitly built to make
progress **now**, decoupled from that upstream schedule, and to adopt core's canonical mechanisms as
they arrive. See [blockers & core dependencies](../research/blockers-and-core-dependencies.md).

## What success looks like

- A published docsite at a `spec-kitty.ai` presence where a visitor can browse every materialized
  pack, read its purpose and artifact inventory, and copy its checksum — all generated.
- A contributor adds a pack by opening a PR with `packs/<name>/` + a small `pack.yaml`; CI validates
  it and the docsite regenerates. The contributor writes **zero** reference docs.
- Maintainers record every material decision as an ADR, and the trust model is explicit and
  auditable.
