# Vision

## The problem this repository answers

Spec Kitty ships a large, multi-domain set of **built-in charter artefacts** as a single monolithic bundle,
and its default behaviour is "activate everything when not explicitly constrained." A consumer
project that skips the (unenforced) charter step inherits the whole corpus and **floods every LLM
session's context** with charter artefacts it does not need.

`spec-kitty-open-packs` replaces the monolith with **coherent, composable, opt-in packs** — domain
and purpose slices a team adopts deliberately, composed both **vertically** (built-in → org →
project) and **horizontally** (independent packs, plus compound stacks shipped as curated **presets
on `built-in`**, not as separate packs that `depends_on` a stack; see epic
[#17](https://github.com/spec-kitty/spec-kitty-open-packs/issues/17)).

## The vision statement

> **`spec-kitty-open-packs` is the canonical, curated, community-friendly publishing home for Spec
> Kitty Charter Packs — where every pack is discoverable, documented straight from its source, and
> verifiable by checksum before it is trusted.**

Three commitments follow from that sentence:

1. **Canonical & curated.** SK Inc. maintains and curates the catalog; community contributions are
   highly welcomed through a low-friction path. This is the single place to find, compare, and pull
   a pack — and the single place to validate one.
2. **Documented from source, not by hand.** The docsite's reference content is **generated from the
   actual code structure** (the pack directories and the validator), so documentation cannot drift
   from reality and adding a pack requires (ideally) **no documentation authoring at all**.
3. **Verifiable by checksum.** Every pack is **checksum-tagged** so a downloaded copy can be
   compared against the published hash — the foundation of a graduated trust story for a repository
   that may eventually ship executable gate assets.

## Where the docsite fits

The docsite is the **public face** of these commitments. It must be:

- **Simple to create and maintain** — a small OSS team should not hand-maintain per-pack pages.
- **Content-from-code** — pack reference pages and the catalog table are generated by walking
  `packs/*/` and running the validator; guides, vision, and decisions are hand-authored and stable.
- **Simple, single-language toolchain** — same Common Docs conventions and the same generate → build →
  GitHub Pages *pattern* core already operates, realized on doc-kitty (Astro), the same stack as the
  spec-kitty-charter site ([ADR](adr/2026-10-17-1-doc-kitty-astro-as-docsite-generator.md)). The
  long-term aim is one look and one maintenance model across both repos by standardizing on doc-kitty/Astro.
- **Trust-surfacing** — each generated pack page shows its integrity block (version, checksum, trust
  tier) so evaluators can judge a pack before adopting it.

## Division of responsibility

Operator ruling, 2026-11-16: packs and their schema, structure and validation are no longer a
concern of the core repository. Core is the deployable, assembler surface; the canonical owner of
the logic is the charter repository; content ownership is in the packs repositories.

| Concern | Lives in |
| --- | --- |
| Charter artefacts, packs, presets (including the compound stacks), **the docsite** | **this repo** (`spec-kitty-open-packs`) |
| Pack authoring & usage guides | **this repo** (`docs/guides/`) |
| Pack schemas and structure, validation, resolution, DRG, activation | the charter ([`spec-kitty-charter`](https://github.com/spec-kitty/spec-kitty-charter)) |
| Assembling and shipping the CLI that consumes the packs | core (`spec-kitty/spec-kitty`) |

Packs follow the charter through one pin: this repository pins a charter commit in
[`charter.lock.yaml`](https://github.com/spec-kitty/spec-kitty-open-packs/blob/main/charter.lock.yaml),
validates every pack against the schemas at that pin, and moves the pin forward as the charter
publishes releases. The pin names a charter release or pre-release tag (`service-v*`) by default,
and the charter's `main` HEAD only on demand (operator ruling, 2026-11-18;
[ADR 2026-11-19-3](adr/2026-11-19-3-pin-charter-releases-and-charter-owns-pack-logic.md)). A core
release is not a gate for pack work; core becomes compatible by consuming the charter.

The July 2026 docsite direction leaned on core work then planned for the manifest schema, the
validator surface and verified distribution. That ownership has since moved to the charter (see
[blockers & core dependencies](../research/blockers-and-core-dependencies.md), kept as a dated
research record). The [docsite design](docsite-design.md) still makes progress decoupled from the
upstream schedule and adopts the canonical mechanisms as they arrive. The themes that deliver this
vision, and their order, are on the [roadmap](../plans/roadmap.md).

## What success looks like

- A published docsite at a `spec-kitty.ai` presence where a visitor can browse every materialized
  pack, read its purpose and artifact inventory, and copy its checksum — all generated.
- A contributor adds a pack by opening a PR with `packs/<name>/` + a small `pack.yaml`; CI validates
  it and the docsite regenerates. The contributor writes **zero** reference docs.
- Maintainers record every material decision as an ADR, and the trust model is explicit and
  auditable.
